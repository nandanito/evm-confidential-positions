## 3. Why Path B failed three times

Attempts 1 and 2 failed the same way, and the Paladin logs show how:
- The sequencer asks the Zeto domain to sign, which for Zeto means generating the proof.
- It cancels the request after about 9–10 s (`PD020100: Request cancelled after 9.9…s`) and
  asks again.
- The first proof then arrives for a request that no longer exists (`Plugin sent response for
  unknown/expired request`), and the loop repeats.

The lines are in [`evidence/node2-sign-timeouts-attempt1.log`](evidence/node2-sign-timeouts-attempt1.log).

The transfers were not lost. Both stuck ones landed, **3.1 and 6.0 min** after Paladin created
them ([`evidence/stuck-transfers-landed.txt`](evidence/stuck-transfers-landed.txt)). By then
the walkthrough had stopped waiting.

The host was under heavy load:
- load average 21–29 (`uptime`);
- the kind worker was swapping, with 11,141 of 11,945 MiB used (`free -m` in the node container);
- liveness probes were timing out on Besu and Postgres (`kubectl get events`).

The failed transcripts are kept as [`evidence/pathB-attempt{1,2,3}.log`](evidence/).

**What this establishes (E-21):** under that load the timeout loop happens, and restarting the
Paladin pods cleared it for the next run. **What it does not:** *why* proving was slow. Memory
pressure is the likely cause, but it is inferred (grade C). No proving time was measured (GAP-2).

**For a reader:** if `npm run example` stops at "Failed while waiting for receipt", check the
host load and the node logs for `Request cancelled` before suspecting the code.
`POLL_MS` raises the walkthrough's wait. Deleting the Paladin pods keeps their state, which
lives on PVCs.
