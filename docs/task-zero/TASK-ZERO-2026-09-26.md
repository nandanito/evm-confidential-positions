|---|---|---|---|---|
| `Zeto_Anon` | hidden (Poseidon commitment) | hidden | **public** — spent commitments appear on chain | none |
| `Zeto_AnonEnc` | hidden; **ECDH-encrypted to receiver on chain** | hidden | **public** | none (encryption is to the receiver, not an auditor) |
| `Zeto_AnonNullifier` | hidden | hidden | **masked** — spend via nullifier + SMT root | none |
| `Zeto_AnonEncNullifier` | hidden; ECDH to receiver | hidden | masked | none |
| `Zeto_AnonNullifierKyc` | hidden | hidden, but proven ∈ registry | masked | none (KYC ≠ auditor) |
| `Zeto_AnonEncNullifierKyc` | hidden; ECDH to receiver | hidden ∈ registry | masked | none |
| `Zeto_AnonEncNullifierNonRepudiation` | hidden | hidden | masked | **yes — encrypted to authority** |
| `Zeto_AnonNullifierQurrency` | hidden | hidden | masked | **yes — ML-KEM to authority (post-quantum)** |
| `Zeto_NfAnon`, `Zeto_NfAnonNullifier` | n/a (NFT) | hidden | direct / masked | none |
| burnable variants | as parent | as parent | as parent | none |

**From whom (chain observer), grade A/C — `zeto-variants.md §2`:**
- Transfer amounts and owner Baby Jubjub public keys are always hidden inside Poseidon
  commitments `Poseidon(value, salt, pkx, pky)`.
- **Deposit and withdraw amounts are public**, and so is the EVM address that calls them —
  this links an on-chain EOA to freshly minted commitments.
- `Zeto_Anon`/`AnonEnc`: the spent input commitments are public, so the UTXO graph is fully
  linkable (docs agree: `anon.md:16`). Nullifier variants hide the spent UTXO among all SMT
  leaves, giving history masking; but the **number of inputs and outputs leaks** through the
  zero padding (a nullifier or output slot = 0), which is public.
- The **submitter (`msg.sender`) is always public and `indexed`** in every transfer event.

This is executed and confirmed for two variants in Q4.

## 3. Issuer / auditor / regulator view — Grade A (source); GAP-1 for execution

**Which variant lets a designated party decrypt?** Only two, and neither ships on the Paladin
devnet:
- **`Zeto_AnonEncNullifierNonRepudiation`.** The circuit encrypts to an *authority* a strict
  superset of what the receiver gets: the input owner's public key, the value and salt of
  every input, every output owner's public key, and the value and salt of every output
  (`anon_enc_nullifier_non_repudiation_base.circom:117-142`). So the non-repudiation authority sees sender,
  receivers, and all amounts of every transfer. Encryption is Baby Jubjub ECDH + Poseidon
  cipher with a public `encryptionNonce`.
- **`Zeto_AnonNullifierQurrency`.** Same plaintext to the authority, but the shared secret is
  established with **ML-KEM-512** (post-quantum). The authority's key is **hard-coded into the
  circuit** (`lib/kyber/kyber.circom:118-128`).

**Fixed at deploy, rotatable?**
- Non-repudiation: the authority key is set by `setArbiter(uint256[2]) onlyOwner`
  (`…non_repudiation.sol:85-87`), **not** in `initialize`. The owner can rotate it at any time,
  **with no event, no timelock and no two-party control**. Past envelopes stay decryptable only
  by the old key. Because the contracts are **UUPS-upgradeable by the owner**, an upgrade can
  change or remove the authority requirement entirely (grade C, follows from UUPS).
- Qurrency: rotation means a **new circuit + new trusted setup + new verifier + redeploy** —
  there is no on-chain key setter.
- **Finding F-3 (this project): WITHHELD.** **Withheld pending coordinated disclosure to Zeto/Paladin** (as of [not yet sent]). The full write-up is held privately until a fix ships or the embargo ends; the row is kept so numbering and links resolve. See `CLAIMS.md` row F-3.

**KYC variant is not an auditor.** `Zeto_AnonNullifierKyc` proves sender and output owners are
members of an owner-controlled registry SMT; it hides *which* member. It grants no decryption.
The registry is `onlyOwner`, publishes every registered key in the clear
(`emit IdentityRegistered`), and **has no revoke function** (`zeto-variants.md §4`).

**Versus XLS-96 (see the comparison doc).** XLS-96's issuer decryption mirror is **mandatory
and non-optional**: the issuer shares its own ElGamal private key, so holders are *never*
private from the issuer (reference P-9). Zeto is the mirror image: the default/deployed
variants have **no** designated decryptor at all; an auditor exists only if you deploy the
non-repudiation or qurrency variant, and even then it is owner-rotatable rather than fixed.
What a Zeto authority can see that XLS-96's cannot: **the full sender+receiver+amount tuple of
every transfer** (XLS-96 amounts are hidden but counterparties are already public on the
ledger, so its auditor's "extra" knowledge is only the amounts). What XLS-96's issuer sees
that a stock Paladin/Zeto deployment does not: **anything at all** — the deployed Zeto variants
expose no plaintext to any third party. <!-- disclosure-ok(P-5): accurate XLS-96 contrast; it says the stock variants have NO view -->

## 4. What a full-chain observer sees — Grade A, EXECUTED (the F-1 equivalent)

Built an observer harness (`tools/observer/observe.ts`) that runs one real transfer on the
live devnet, then reads every base-ledger field from Besu directly and contrasts it with what
the sending node privately holds. Run for two deployed variants on 2026-09-26, and **re-run
on 2026-09-27** after a Codex review hardened the harness (it now fails loudly on ABI/decode
mismatches, keeps the raw tx/receipt/block objects alongside the decoded fields, and checks
receipt status and `tx.to`, and keeps the tx signature). The committed outputs are from the
latest re-run (the third, after a second Codex verification round):
`tools/observer/observer-out-anonnullifier.json`, `observer-out-anonenc.json`.

**`Zeto_AnonNullifier`, transfer of 1000 (bank1→bank2), base-ledger tx
`0xd8ba191f…` (committed run; earlier runs `0xa3a06135…`, `0xfbba50a5…`):** a full-chain
observer reads, in the clear:
- **Submitter EOA** `0xFd033c1A762936a5e14293c13406D07010235070` (also an `indexed` topic on
  the `UTXOTransfer` event) — the Paladin node's submit key, not the owner. Each of the three
  runs deployed a fresh token contract and each had a different submitter (`0x5761…`,
  `0x0C27…`, `0xFd03…`), as the code's `domains.<contractAddr>.submit.<uuid>` identity predicts
  (observation, not a proof of the rotation rule).
- Contract address, nonce, the tx signature, gas, block number and **timestamp**. Gas here is
  **data-dependent** (1,381,377 / 1,381,377 / 1,715,535 across three runs) — see §6.
- `transfer(nullifiers[2], outputs[2], root, proof, data)`: two nullifiers **one of which is
  `0`** (padding → this spent exactly one real note), two output commitments, the SMT `root`,
  a Groth16 proof (8 field elements), and a `data` blob. calldata = 772 bytes.
- Event `UTXOTransfer(inputs=[nullifier,0], outputs=[c,c], submitter, data)`.

The observer does **not** see: the amount (1000), the change (99000), or either party's Baby
Jubjub key. Those live only in the node. The node privately holds (from the same receipt): the
spent coin `{amount:100000, owner:0xc589…}`, the new coin `{amount:1000, owner:0xb0d8…}` to
bank2, and the change `{amount:99000, owner:0xc589…}` back to bank1 — plus SMT internal nodes.

**`Zeto_AnonEnc`, transfer of 1000, base-ledger tx `0x370054b0…` (earlier `0x8bb2e6b5…`, `0x2c33eda3…`):** additionally puts on chain
the event `UTXOTransferWithEncryptedValues` with the **ECDH ephemeral public key**, the
**`encryptionNonce`**, and **8 field elements of Poseidon-encrypted `[value,salt]` pairs** for
the outputs — decryptable **by the receiver** (the counterparty), not by an observer and not by
an auditor. gasUsed 412,957 / 412,975 / 412,957 across three runs: the 18-gas spread is
calldata byte content — the ciphertext is random and EVM calldata costs 4 gas per zero byte,
16 per non-zero; calldata 1156 bytes.

**Node-private data (re-run).** The receipt's state lists carry the coins; the Zeto
*domain receipt* call returns `PD210102: Not implemented. See state receipt for coin transfers`
on Paladin v1.0.0 (the original harness silently reported it as "absent"). The owner keys are
identical across all three runs (`0xc589…`, `0xb0d8…`), as HD derivation from the node mnemonic implies.

**Leak summary (executed):** amounts and identities are hidden; **but the submitter EOA,
timing, gas, note counts (via padding), the SMT root, and — for AnonEnc — the on-chain
receiver ciphertext are all public.** The parallel to XLS-96 F-1: there, the "reset inbox
value" was recomputable by any observer; here, the analogous public artifact is the submitter
identity + note-count padding + gas fingerprint, which together leak transaction *shape* and a
persistent-per-epoch submitter address even when amounts are hidden.

## 5. Trust assumptions — Grade A, see `paladin-trust.md`, `zeto-variants.md §5`

**Trusted setup (the sharpest one).** Zeto uses **Groth16, one trusted setup per circuit**
(`gen.js:211`). The checked-in verifier contracts and the shipped proving keys are generated
with **`snarkjs groth16 setup` and no phase-2 contribution** — Zeto's own README calls them
"**UNSAFE** proving keys that should NOT be used in production" (`zkp/circuits/README.md:109,125`).
Verified independently: in **30/30** verifier contracts at HEAD (and 32/32 at v0.2.2) the
`delta` G2 point equals `gamma` (both the BN254 generator), and the same constants appear in
the verifier **deployed on our devnet** (confirmed against on-chain bytecode). With δ=γ known,
forging Groth16 proofs is a known result — so the deployed verifiers are unsound for real value
(grade C for the forge step; A for δ=γ). This is a public, acknowledged issue: Zeto #186 (open),
maintainer considers the README warning "sufficient." **A production deployment must run its own
ceremony**; Paladin ships Zeto's test keys unchanged (`paladin-trust.md §4`) and documents no
ceremony. The qurrency circuit even commits the auditor's ML-KEM **secret** key for testing
(`zkp/js/lib/testKeypair.js`).

**The Paladin node's role.** Proofs are generated **inside the sender's own node**, in-process,
with the raw Baby Jubjub private key pushed into the Zeto domain plugin (`libzeto.so`)
(`paladin-trust.md §1`). There is **no notary or endorser** in the Zeto domain — the only
attestation step is the sender's own proof. The node also submits the base-ledger tx, signed by
a **per-coordinator-epoch** key `domains.<contract>.submit.<uuid>` (default epoch = 100 blocks),
**not** a fresh key per transaction — the docs claim per-transaction and the code disagrees
(`paladin-trust.md §1`, grade A code-vs-doc).

**Where keys live.** Two keystores only: `filesystem` (keystorev3, password in a `.pwd` file
next to the key) and `static` (unencrypted in config). HD derivation (BIP32/39/44). **No HSM /
PKCS#11 / KMS is implemented** — only described in docs. The devnet/operator default: the
operator generates one BIP39 mnemonic per node and stores it **unencrypted in a Kubernetes
Secret**; that one mnemonic controls **every** EVM and Baby Jubjub key on the node
(`paladin-trust.md §2`).

**What a compromised node learns / can do (grade A/C).** A node is multi-tenant with no
isolation between users, and devnet configures no RPC auth. A compromised node, pod, or its
K8s Secret: **sees every local user's coin data (amounts, owners) and full history in
plaintext** (Postgres `states.data` / `transactions.data` are plaintext), and **can spend every
local user's funds** (it holds/derives all keys and runs the prover). A DB-only compromise
yields data but no keys. A compromised counterparty node learns only the coins sent to it plus
the info state (`from,to,data`). Inter-node transport is gRPC **mTLS-only**, but peer identity
is verified against the **on-chain registry** (self-signed certs), so trusting a peer = trusting
the registry; coin states travel as **plaintext JSON inside the TLS channel** with no
application-layer encryption (`paladin-trust.md §1,§6`).

## 6. Proof size, gas and latency — Grade A, EXECUTED (hardware + method stated)

All on Apple M3 Pro (12 cores, 18 GB), macOS 26.6.2. Full logs in
`sources/bench-proof-2026-09-27-runs20.log` (current) and `sources/bench-proof-2026-09-26.log`
(superseded); harness `tools/observer/bench-proof.js`.

**Proof size.** Groth16 on BN254 → **256 bytes on the wire, invariant** (A(2)+B(4)+C(2) field
elements × 32 B), regardless of circuit. Confirmed for `anon` and `anon_enc`. (The reference
XLS-96 Send proof is 946 B — larger, because Bulletproofs are not constant-size the way a
Groth16 proof is; but XLS-96 needs no trusted setup.)

**Proof-generation latency (snarkjs 0.7.5, shipped v0.5.1 release proving keys, 20 runs,
every proof verified, 2026-09-27):**

| Circuit | Witness calc (median) | Groth16 prove: median (min–max) | Public signals |
|---|---|---|---|
| `anon` (Zeto_Anon) | 41.9 ms | **326 ms** (251–563) | 4 |
| `anon_enc` (Zeto_AnonEnc) | 89.7 ms | **851 ms** (724–1620) | 15 |

**Load, stated:** these ran with the kind devnet up; load average was 12–15 on 12 cores, which
is why single proves vary ~2×. Treat the medians as loaded-machine figures, not best case.
*Superseded:* the 2026-09-26 figures (371.6 / 1029 ms) were 6 runs, used an upper-middle rather
than true median for even sample counts, and verified only the last proof — all three fixed in
the harness after the Codex review. Encryption roughly 2.6× the proving time. Nullifier-variant isolated proving time: GAP-2.

**On-chain gas (Besu 25.8.0, QBFT, `min-gas-price 0`, so these are pure execution gas):**

| Operation | Variant | gasUsed, three runs on fresh contracts | txs |
|---|---|---|---|
| mint (2 outputs) | Zeto_AnonNullifier | 396,399 · 396,399 · 396,399 | `0x2ba88291…` `0x20b5fd51…` `0x8c8e6db8…` |
| **transfer** | Zeto_AnonNullifier | **1,381,377 · 1,381,377 · 1,715,535** | `0xa3a06135…` `0xfbba50a5…` `0xd8ba191f…` |
| mint (2 outputs) | Zeto_AnonEnc | 60,213 · 60,213 · 60,201 | `0x82bd2b4f…` `0x0c9f21a7…` `0x5aa3d1a5…` |
| **transfer** | Zeto_AnonEnc | **412,957 · 412,975 · 412,957** | `0x8bb2e6b5…` `0x2c33eda3…` `0x370054b0…` |

**The nullifier transfer's gas is data-dependent, not a constant.** Every run had the same
shape (one real nullifier, two outputs, 772 calldata bytes). The spread comes from the
sparse-Merkle-tree insert: `SmtLib._pushLeaf` recurses once for every low-order bit a new leaf's
index shares with the colliding existing leaf, adding a middle node (hash + storage write) per
level. Leaf indices are random commitments, so the extra depth is geometric — most inserts are
shallow, occasionally one is deep. Mechanism grade A (code read, `kaleido-io/contracts@keccak256`
`SmtLib.sol:456-540`, plus three observations); the distribution itself is not measured — budget
nullifier transfers with headroom, not at 1.38 M. *(2026-09-27: two example runs, `example/run.ts`,
observed 1,486,600 · 2,308,044 · 1,568,849 and 1,464,684 · 1,902,372 · 1,454,834 on six more transfers —
above this table's maximum — so the observed range is now 1.38 M–2.31 M over nine; `CLAIMS.md` E-10.)* The first mint into an empty tree has nothing
to collide with, hence its constant 396,399. The AnonEnc spreads (≤18 gas) are calldata content.
*Corrected 2026-09-27:* an earlier revision of this section said these figures "reproduced
exactly" after two matching runs; the third run disproved it.

The nullifier variant's transfer costs ~3.3–4.2× the AnonEnc transfer in these three runs (~3.3–5.6× across all nine once the 2026-09-27 example runs are included, `CLAIMS.md` E-10), and its mint ~6.6× the
AnonEnc mint, because of the on-chain Sparse-Merkle-Tree inserts and the nullifier
verification. Deployed verifier-contract sizes range 1.9–20.9 KiB (qurrency batch the largest);
the sizer table ran under `hardhat size-contracts`.

**Latency caveat.** These are proving/gas numbers, not end-to-end. End-to-end transfer wall
time on the devnet also includes QBFT block time (~1–2 s) and node state indexing; not isolated
here.

**What should change in the plan:**
1. **Trusted setup is the gating decision, not a footnote.** Unlike XLS-96 (Bulletproofs, no
   ceremony), any Zeto deployment that holds real value needs its own Groth16 phase-2 ceremony
   per circuit. Budget for it, and never demo on the shipped test keys as if they were real.
2. **The confidentiality model is UTXO + no-default-auditor**, the inverse of XLS-96's
   account + mandatory-issuer-mirror. If the project needs a regulator view, that is an explicit
   variant choice (non-repudiation / qurrency) with an owner-rotatable, non-fixed authority —
   and that owner power (mint, setArbiter, UUPS upgrade) is itself a trust assumption to name.
3. **The Paladin node is the trust boundary.** It holds keys, proves, and stores plaintext coin
   data; one mnemonic per node controls everything and devnet has no auth. Any threat model must
   treat node/operator compromise as total loss for that node's tenants.
4. **Paladin pins Zeto v0.2.2** (Jan 2026), 329 commits behind Zeto HEAD. Design against the
   pinned behaviour, not the latest Zeto docs.
5. **Nothing is audited (public corpus).** Do not call anything audited, production-ready, or
   secure. The δ=γ test-key issue alone is disqualifying for value-bearing use.
